# Contract: Transaction event message

The wire format of a transaction event. **This document is the contract.** Under Principle I the two services share no code, so each parses this format independently — this file is the only thing that keeps them agreeing, which makes it the one place a change must be made deliberately.

## Format

JSON object, UTF-8, published with content type `application/json`.

```json
{
  "event_id": "4f1d2e8a-3c7b-4a19-9f02-6e5d8b1c7a40",
  "occurred_at": "2026-10-31T14:22:31.482Z",
  "account_id": "card_000127",
  "amount": "4250.00",
  "merchant": "Northwind Electronics"
}
```

## Fields

| Field | Type | Required | Rules |
|---|---|---|---|
| `event_id` | string, UUID | yes | Unique per event. Generated by the Producer. This is the idempotency key — the Worker uses it as the decision table's primary key, so a repeated `event_id` is treated as the *same* transaction, never a new one. |
| `occurred_at` | string, RFC 3339 / ISO 8601 with timezone | yes | When the transaction happened, as the Producer reports it. Must carry an explicit offset (`Z` or `±hh:mm`) — a naive timestamp is ambiguous and is grounds for rejection. |
| `account_id` | string, non-empty | yes | The card or account. Opaque; no format is imposed and no account registry exists. |
| `amount` | string, decimal | yes | **A string, not a JSON number.** See below. |
| `merchant` | string, non-empty | yes | Free text. Not used by any rule; carried so a stored decision is readable on its own. |

## Why `amount` is a string

JSON numbers are IEEE 754 doubles in most parsers, and `0.1 + 0.2 != 0.3` in binary floating point. Money must not be held in a type that cannot represent it exactly, and a threshold comparison at the boundary — which the rules contract requires to be exact — is precisely where a floating-point error would show up as a wrong verdict that is almost impossible to reproduce.

So the amount crosses the wire as a decimal **string** and is parsed into Python's `Decimal` and stored as PostgreSQL `numeric(12,2)`. Both are exact decimal types. The cost is one conversion at each end; the benefit is that the boundary case means what it says.

`numeric(12,2)` allows up to 10 digits before the decimal point, which is far beyond any plausible card transaction and leaves the spec's "enormous amount" edge case decidable rather than an overflow.

## Validation, and what happens when it fails

The Worker must **reject into the dead-letter queue** (never drop, never requeue) a message that:

- is not valid JSON
- is not a JSON object at the top level
- is missing any required field
- has an `event_id` that is not a valid UUID
- has an `occurred_at` that is not parseable, or carries no timezone offset
- has an `amount` that is not a valid decimal
- has an empty `account_id` or `merchant`

Each rejection must be logged with the reason and, where it could be read, the `event_id` — a dead-lettered message nobody can explain is barely better than a dropped one.

## Unknown fields are accepted

A message carrying fields not listed here **must be processed normally**, with the extra fields ignored.

This is a compatibility rule with a specific purpose: it means a future Producer can add a field and be deployed before the Worker that understands it, without every in-flight message becoming poison. The reverse — rejecting unknown fields — would make the two services' deployment order a correctness concern, and they are supposed to be independently deployable (Principle I).

The spec lists this as an edge case, and it is tested.

## Changing this contract

The services are deployed independently, so at any moment during a change one may be newer than the other.

- **Adding an optional field** is safe in either order, by the rule above.
- **Adding a required field, renaming one, or changing a type** is not: an old Worker will dead-letter the new messages, or a new Worker will dead-letter the old ones. Such a change needs either a transition where the field is optional and both are deployed, or a new queue.
- There is deliberately **no version field** in the payload. Adding one now would be speculative (Principle V) and it would not help: the Worker cannot act on a version it does not understand, and the unknown-field rule already covers additive change. If an incompatible change ever becomes necessary, a new queue name is the clearer mechanism, because it keeps the old and new streams separable.

Per the constitution, a change to this contract must be made in the same change as the code that depends on it.
